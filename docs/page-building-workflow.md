# 인터뷰 → AEO/GEO 페이지 생성 워크플로 (범용 SOP)

> **목적:** 0(빈 상태)에서 시작해 **AI가 질문 → 사용자가 답 → 그 답을 재료로 AEO/GEO 최적화 페이지를 생성**한다.
> 즉 이 문서는 "페이지를 예쁘게 만드는 법"이 아니라 **"답변엔진·생성AI가 인용하는 페이지를 인터뷰로 뽑아내는 법"** 이다.
> **글(본문) 작성은 항상 `docs/aeo-geo-writing-prompts.md`의 프롬프트 8단계를 순서대로 적용한다**(단계 대응표는 그 문서 하단).
> 최적화의 기준과 구현은 **fire-your-seo-agency 스킬**(`references/aeo.md·geo.md·llmo.md`)을 적용한다. 이 문서는 그 스킬을 "인터뷰 → 승인 → 발행" 흐름에 끼운 운영 절차다.
>
> 본문(0~6단계)은 **주제·사이트에 종속되지 않는다.** 배포 대상(어느 사이트/레포)도 인터뷰에서 정하는 변수다.
> 특정 프로젝트의 규칙·용어·명령·배포지는 맨 아래 **[부록 A — 프로젝트 기본값]** 블록에 모아둔다. 새 프로젝트는 그 블록만 추가하면 된다.

---

## 이 문서를 읽는 법 (한눈에)

제작은 **6단계**이고, 각 단계 사이에 **사용자 승인(🚦 게이트)** 이 있다.
승인 없이 다음 단계로 넘어가지 않는다. "코딩 → 보여주기 → 승인 → 코딩"의 반복이다.

```
0. 요청 접수
   0-A 프로젝트 컨텍스트 확인 (어느 프로젝트? 기본값 있나?)  ← 최초에 반드시
   0-B 페이지 요청 접수 (목적·타겟·행동…)
   🚦 게이트 A: 기획안으로 진행
1. 기획안 작성    → 구조·카피 방향 제시 (코딩 전)
   🚦 게이트 B: "이 구조로 ㄱㄱ"
2. 1차 코딩(초안) → 만들고 프리뷰로 보여줌
   🚦 게이트 C: 피드백 / 수정 요청
3. 수정 루프      → 피드백 → 코딩 → 프리뷰 (반복)
   🚦 게이트 D: 최종 승인 ("발행해도 돼")
4. 발행 전 QA     → 체크리스트 자동 점검
5. 발행 & 검증    → 발행 → 라이브 확인 → 색인 제출
6. 측정           → 재측정 예약
```

## 산출 기준 — 모든 페이지가 만족해야 할 AEO/GEO 요건

이 워크플로의 결과물은 "답변엔진·생성AI가 인용할 수 있는 페이지"다. 1단계 기획과 2단계 코딩은 아래를 **설계 목표**로 삼고, 4단계 QA에서 **검증**한다. (근거: fire-your-seo-agency `references/aeo·geo·llmo`)

1. **질문 = 페이지.** 제목·H1·URL이 사람들이 실제로 검색창/AI에 던지는 **자연어 질문**을 반영한다. (내가 쓰고 싶은 말❌ → 고객이 치는 말⭕)
2. **직답 먼저.** 첫 문단(또는 `answer`)에 결론을 40자 내외로. 그 아래에 근거(표·수치·기준일). 설명부터 시작하지 않는다.
3. **인용 가능한 1차 소스.** AI는 잘 쓴 글이 아니라 **정확한 사실·숫자**를 인용한다. 이 페이지가 **원출처가 될 사실 하나 이상**을 담는다(없으면 인터뷰에서 끌어낸다). 과장·거짓은 인용 신뢰를 죽인다.
4. **구조화 데이터.** FAQPage / Article / Service 등 + `@id` 엔티티 그래프. **화면 내용과 반드시 일치**(거짓 JSON-LD 금지).
5. **크롤러의 눈으로 노출.** 자바스크립트 없이 받은 HTML에 h1·본문·메타·구조화 데이터가 실제로 있어야 한다("코드에 있다"가 아니라 `curl`로 보인다가 기준).
6. **발견 경로 반영.** 사이트맵·llms.txt·내부링크에 연결(색인 대상일 때). 광고 랜딩은 noindex + 사이트맵 제외.
7. **측정 가능.** 노출·클릭(검색 콘솔)과 전환(목적 행동)·AI 인용 O/X를 뒤에 잴 수 있게 둔다.

> 이 7개가 "AEO/GEO 최적화됨"의 정의다. 디자인·카피는 이 요건을 해치지 않는 선에서 자유롭게.

## 0-A단계 — 프로젝트 컨텍스트 확인 (최초에 반드시)

**가장 먼저 "이게 어느 프로젝트인가"를 확정한다.** 이게 이 템플릿을 범용으로 쓰는 핵심이다.

> **기본값은 "새 페이지 제작"이다.** 기존 사이트(더베이직플랜 포함)에 올린다고 **절대 가정하지 않는다.**
> 사용자가 명시적으로 "더베이직플랜에 / 이 사이트에 올려줘"라고 하기 전에는, 배포 대상을 특정 사이트로 전제하거나 "거기 올릴까요?"라고 유도 질문하지 않는다.

1. **어느 프로젝트/주제인가?** (이게 정해지기 전까진 배포지를 가정하지 않는다)
   - **기본 = 새 페이지/프로젝트** → 아래 2~7을 물어 부록 A에 새 블록을 만든 뒤 진행. 배포 대상도 이때 함께 정한다(새 사이트/레포인지, 기존 어디인지).
   - 사용자가 **명시적으로 기존 프로젝트를 지목**(예: "더베이직플랜에")하면 → 부록 A의 해당 블록을 로드하고 0-B로. (지목 안 하면 로드하지 않는다)

**새 프로젝트일 때만 묻는다 (기본값 블록 1회 작성용):**
2. **도메인/비즈니스 한 줄** — 무엇을 하는 곳인가, 무엇을 파는가.
3. **타겟 독자** — 누구를 위한 페이지인가.
4. **포지셔닝/전략 문서** — 참고할 상위 전략 문서가 있나? (있으면 경로 → 작업 전 먼저 읽는다)
5. **스택·레포·발행 방식** — 무슨 프레임워크(Astro 등), 레포 위치, 어떻게 배포되나(빌드 명령·배포 트리거·색인 제출).
   - **새 사이트(0에서 시작)면 검색엔진 등록이 아직 안 된 상태다.** 첫 배포 직후 아래를 5단계에서 반드시 처리한다(빠뜨리면 산출 기준 7 "측정 가능"이 깨진다).
     구글 서치콘솔(vercel.app 같은 서브도메인은 "URL 접두어" 속성) · 네이버 서치어드바이저 → 소유확인(HTML 태그 방식: 사용자가 로그인해 meta 태그를 받아 전달 → Claude가 사이트에 넣고 재배포 → 사용자가 "확인") → 사이트맵 제출 → IndexNow 키 세팅.
     로그인·확인 버튼은 사용자 계정 작업이므로 사용자가 직접 한다.
6. **하우스룰** — 말투/톤, 쓰지 말 표현, 지켜야 할 규제(예: 광고법)·브랜드 규칙.
7. **행동/의심 프레임** — 이 프로젝트가 쓰는 퍼널 단계나 "반대 이유" 모델이 있나? 없으면 일반형(발견→비교→전환)으로 간다.

> 요점: **주제는 매번 바뀔 수 있다. 프로세스는 안 바뀐다.** 바뀌는 것(용어·규칙·명령)은 전부 부록 A로.

## 0-B단계 — 페이지 요청 접수 (Claude가 묻고, 사용자가 답한다)

프로젝트가 정해지면, 이 페이지 한 장에 대해 확인한다. 이미 대화에 있으면 다시 묻지 않는다.

1. **목적 한 줄** — 이 페이지는 무엇을 하게 만드는가?
2. **타겟** — 누가 보는가? (프로젝트 기본 타겟과 다르면 명시)
3. **여정 위치** — 발견 / 비교·검토 / 행동(문의·구매) 중 어디? (프로젝트에 퍼널 모델 있으면 그 단계로)
4. **제거할 반대 이유** — 보는 사람이 "안 할 이유" 중 무엇을 없앨 페이지인가? (의심 프레임 있으면 그걸로)
5. **원하는 다음 행동(CTA)** — 본 뒤 바라는 한 가지 행동.
6. **색인 여부** — 검색 노출용인가, 아니면 **광고 랜딩이라 noindex**(사이트맵 제외)인가?
7. **URL** — 원하는 주소. 없으면 Claude가 제안.
8. **실제 질문(AEO 재료)** — 사람들이 이 주제로 검색창/AI에 **실제로 치는 자연어 질문** 3~5개. (모르면 Claude가 후보를 제시해 고르게 한다) → 제목·H1·FAQ의 뼈대가 된다.
9. **인용 가능한 사실(GEO 재료)** — 이 페이지가 원출처가 될 수 있는 **구체적 사실·숫자·절차** 하나 이상. (가격·단계·기준·기간 등. 없으면 인터뷰로 끌어낸다)

**사용자가 줄 자료 (있으면 다 주세요 — 많을수록 정확):**
- 참고 카피/문구, 참고 디자인(경쟁사/사이트 링크·스샷), 넣을 실제 정보(가격·절차·FAQ·연락 수단), 피할 표현.

> 자료가 부족해도 된다. 초안을 보여주고 고치는 게 완벽한 사전 설명보다 빠르다.

### 🚦 게이트 A → 1단계

## 1단계 — 기획안 작성 (코딩 전, 제시 → 승인)

**아직 코딩하지 않는다.** 아래를 글로 제시한다(표·목록, 1~2분에 읽히게):
1. **목적·타겟·여정·반대이유** (0단계 정리본)
2. **인식 변화** — 보기 전 믿음 → 본 뒤 새 판단 한 줄.
3. **AEO/GEO 매핑** (산출 기준 1~3 적용) — 주 질문(=제목·H1), 직답 한 줄(40자), 인용 사실 하나, FAQ 질문 3~5개. → 이게 페이지의 뼈대다.
4. **섹션 구조(와이어프레임)** — 위→아래 섹션 이름 + 각 한 줄 역할. (직답을 맨 위, 근거를 그 아래로)
5. **카피 톤** — 말투, 강조/금지.
6. **CTA 동선** — 버튼이 어디로.
7. **기술 메모** — 구조화 데이터 타입(FAQPage/Article/Service)·엔티티 그래프, 측정 이벤트, 색인/noindex.

### 🚦 게이트 B
사용자가 **"이 구조로 ㄱㄱ"** 또는 수정. 승인 전 코딩 금지. 방향이 크게 틀어지면 1단계 재작성.

## 2단계 — 1차 코딩 (초안 → 프리뷰로 보여주기)

1. 페이지 파일 작성 (기존 컴포넌트·스타일 패턴 재사용 — 부록 A의 스택 참조). **산출 기준 1~5를 코드에 반영**: 질문형 제목·H1, 직답 먼저, 인용 사실, 화면과 일치하는 구조화 데이터, SSR 노출.
2. 필요 시 내비게이션/구조화 데이터/측정 이벤트 연결. (fire-your-seo-agency 스킬 aeo/geo/llmo 체크 적용)
3. 빌드 → 에러 0 확인. 프로젝트에 검증 스크립트 있으면 실행.
4. **보여주기** — 로컬 프리뷰 화면/스크린샷, 또는 미리 배포해 라이브 URL(폰 확인용).

> 산출물은 "초안". 완성이 아니라 보여주는 게 목적.

### 🚦 게이트 C
사용자 피드백("문구 바꿔 / 섹션 빼 / 색 바꿔").

---

## 3단계 — 수정 루프 (피드백 → 코딩 → 프리뷰, 반복)

- 한 번에 큰 덩어리씩 바꾸고, 바꾼 것만 짚어 보고(before/after).
- 만족할 때까지 반복.

### 🚦 게이트 D — 최종 발행 승인
명시적 승인("발행해")이 있어야 발행. (발행 = 외부 공개, 되돌리기 어려움)

---

## 4단계 — 발행 전 QA (통과 못 하면 보류)

- [ ] 빌드 에러 0 / 프로젝트 검증 스크립트 통과
- [ ] 크롤러의 눈: 빌드된 HTML(JS 없이)에 h1·본문·메타·구조화 데이터가 실제로 있는가
- [ ] 색인 의도 일치: 노출용=index, 광고 랜딩=noindex + 사이트맵 제외
- [ ] 구조화 데이터가 화면 내용과 일치(거짓 데이터 금지)
- [ ] CTA 링크가 실제 목적지로 감(폼 URL 등 안 깨짐)
- [ ] 측정 이벤트 연결 확인(이벤트 유실 함정 주의)
- [ ] 추상어를 관찰 가능한 행동으로, 근거 없는 숫자·과장·보장 없음
- [ ] 부록 A의 하우스룰·규제 준수 (톤·금지표현·광고법 등)
- [ ] 모바일 레이아웃 안 깨짐

---

## 5단계 — 발행 & 검증

부록 A의 발행 명령을 따른다. 일반 뼈대:
```
git pull --ff-only → git add → git commit(올바른 author 이메일) → git push(배포 트리거)
→ 라이브 200 확인(폴링) → 색인 제출 스크립트 실행
```
발행 후 필요 시 **내비게이션·llms.txt·관련 내부링크**에 새 페이지 반영. (광고 랜딩은 색인/사이트맵 제외)

**새 사이트의 첫 발행이면 추가로:** 검색엔진 등록·소유확인·사이트맵 제출(0-A 5번 참고). 사용자에게 순서를 안내하고, 받은 소유확인 meta 태그를 넣어 재배포한 뒤 완료까지 확인한다.

**보고 형식:** ① 만든 것(URL) ② 크롤러 눈 검증(라이브 200·핵심요소) ③ 반영한 연결 ④ 다음 측정 일정.

---

## 6단계 — 측정 (고치고 끝이 아니다)

발행 = 기준선. **재측정 날짜를 예약**한다(기본 14일 뒤). 노출/클릭(검색 콘솔류)·전환(목적 행동 수).
"고쳤다"가 아니라 "언제 무엇을 다시 잰다"까지가 완료.
